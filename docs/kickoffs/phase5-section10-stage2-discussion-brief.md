## 二、實測證據（探針已入 repo，可獨立重跑）

### A. 攔網的時間預算

`node tools/phase5-block-timing-probe.mjs 12 read`（12 局，B 隊 MB 視角，單位 tick／60Hz）

| 量 | quick | wing |
|---|---|---|
| `setToHit` 二傳觸球→擊球 | **p50 = 32** | p50 = 81 |
| `delay` 反應延遲 `max(6, 24−reaction×0.16)` | **14** | 14 |
| `planLag` →鎖定成立 | 15 | 15 |
| `winOpen` →**攔網窗開啟** | **33** | **82** |

**兩個關鍵讀法：**

**① `winOpen ≈ setToHit + 1`，兩種人格都一樣。**
攔網窗的開啟條件是 `r.profile === 'spike'`，而 `profile` 要到**攻擊手把球打出去**才變成
`'spike'`。所以現況是：

> **攔網手的起跳觸發，是「對方已經把球擊出」這件事本身。**

實作端已把起跳改掛在判定上（`planX != null`），**開窗時點一格沒動**——因為
`profile === 'spike'` 才是更晚的那個約束。

**② read 的延遲吃不掉快攻的預算。**
read 在 `set+15` 決定；快攻擊球在 `set+32`、球過網約 `set+38`。
即使再加上已實作的 12 tick 重新踩定代價（`set+27`），距離球過網仍有 **11 tick** 餘裕。
`delay 14` 只佔快攻預算 `32` 的 **44%**。

> 憲法 §零 寫「read 加上決策延遲後，面對快攻他會晚 10–25 tick 起跳＝手還在球下面」。
> **這個推論在現況的時間尺度下不成立。**

### B. `blockTimingMul` 現在是一顆死旋鈕

檔位：`晚(1)=0.6`／`甜蜜(12)=1.0`／`早(40)=0.55`

實測 read 有跳者的時機分佈：

```
太晚(<4)  6.0%     甜蜜(4-26) 94.0%     太早(>26) 0.0%
```

因為觸發（擊球）與結算（球過網）之間恆隔那幾 tick，**時機不可能不對**。
這顆旋鈕現在等於恆為 1.0。

### C. E 表兩次嘗試的結果

基準（改制前）：面對快攻 read **100.0%** ／ commit **93.7%**
（指標＝`block-persona-probe` 的「MB 在攔網範圍內%」）

| 版本 | 目標 x 的來源 | 快攻 read | 快攻 commit | 反轉？ |
|---|---|---|---|---|
| v1 | 攻擊手**身體 x**（`blockCommitRead`） | 50.6% | **82.7%** | ✅ |
| v2 | **球的預測擊球點**（`predictContactPoint`） | 99.1% | 84.8% | ❌ |

**v1 反轉了，但要一併看兩翼**：v1 的 read 面對兩翼，MB 落差 p50 達 **3.39m**——
因為 `blockCommitRead` 取「最接近網、且正在推進」者，**中路的假動作誘餌恆勝**，
read 被誘餌釘在中間。這使 read 在高球局面荒謬地無能，與憲法對 read 的定義
（「賭看清楚再動來得及」）矛盾，且翻掉了 `block-persona.test.mjs` 的既有行為斷言
（「commit 的中間攔網手離球較遠」方向反了）。

**v2 修掉了誘餌問題**（兩翼 read 落差 p50 3.39m → **0.35m**，符合憲法對 read 的定義），
但快攻的 E 表就不反轉了——因為 read 拿到球的拋物線後資訊完全足夠，而時間又不構成懲罰（見 A、B）。

> v2 用的 `predictContactPoint(game.ball, …)` 只吃球的物理量，
> **拿不到 `attackerId`**，反作弊靜態掃描仍綠。球的拋物線是場上每個人都看得見的公開資訊，
> 且**二傳觸球前不存在**——所以 commit 用不了它，只能從助跑猜。這正是兩種人格的誠實分野。

## 三、推理鏈：為什麼「砍 timing 幾何化」會讓這一環變假

```
E 表要反轉
  ⇒ read 面對快攻必須真的吃虧
    ⇒ 吃虧只能來自「位置」或「時機」
      ⇒ 位置行不通：快攻在中路，而 MB 的陣型基準位**就是**中路
        （量測 v2：read 面對快攻落差 p50 0.21m——他根本不必移動）
      ⇒ 只剩時機
        ⇒ 但「跳了就等於手在頂點」⇒ 晚跳 10 tick 照樣攔得到（量測 B：94% 甜蜜）
          ⇒ 除非**跳起來需要時間才到頂** ＝ timing 幾何化
```

**接上幾何化之後，E 表的四格全部由幾何長出來，一顆旋鈕都不必轉：**

| | 面對快攻 | 面對兩翼高球 |
|---|---|---|
| **read** | 二傳觸球後才決定 → 晚跳 → 球過網時手**還在上升** → 夠不到 | 時間充裕，跳在頂點 → 攔得到 |
| **commit** | 二傳觸球前就跟死 → 已在頂點 → **攔得到** | 猜錯人，站在錯的地方（幾何）→ 漏 |

「手還在球下面」不再是形容詞，而是 `blockReach` 真的還沒升上去。
符合協議 7（多人／時機加成由幾何湧現）與協議 3（不靠隱形補償）。

### 不選另外兩條路的理由

| 路 | 為什麼不選 |
|---|---|
| 調 `REPLANT_TICKS`（12→18+）讓 read 遲到 | 它在白名單上，但這是**拿旋鈕湊目標數字**。協議 1 明寫「不得沿用現值反推」，協議 6 說旋鈕要在階段五**一起**擰。為了讓 E 表好看先擰一顆，等於把平衡手段偽裝成機制——本卷最不該犯的錯 |
| 另立一個更長的攔網專用延遲常數 | 工單 §2.4-c 明令「延遲沿用 `max(6, 24−reaction×0.16)`，**不得另立常數**」 |

## 四、順帶挖到的 repo 級缺陷（與本題獨立，但影響驗收）

`core.autocrlf = true`（系統層，Git for Windows 預設）＋ **無 `.gitattributes`** ＋ repo 內存 LF
⇒ git 一旦碰過工作區檔案就轉成 CRLF
⇒ 反作弊護欄測試 `block-persona.test.mjs`「B1-SCAN 區零 `attackerId`」**變紅**，
而 `blockRead.js` 內容與 `fa7e3f4` **逐字相同**。

根因：護欄的剝註解正則 `/\/\/.*$/` 在 CRLF 行上失效
（JS 的 `.` 不匹配 `\r`——它是行終止符；`$` 也不在 `\r` 前面），
於是註解裡的 `attackerId` 沒被剝掉，誤判成作弊。

> **任何人在 Windows 用預設 git 設定 clone 這個 repo，這條護欄都會紅。**
> 工單 §11 的前提是「Sawmah 可獨立驗證，不採自我回報」——一個 fresh clone 就會紅的護欄，
> 等於那條驗收線是假的。

現況：已把 325 個被轉成 CRLF 的追蹤檔還原為 LF，main 回綠（771 pass）。
**已改動一項本地 git 設定**：`core.autocrlf=false`（僅此 repo）——治標，加了 `.gitattributes` 後可還原。

## 五、附帶小題 b：`reachAssist` 建議「留」的三個理由

1. **它不是平衡手段，是顯示誠實。** 它做的事是讓角色的手真的伸向球，不是放寬判定，
   正是顯示哲學「狀態誠實呈現」要的。階段五把可及縮到 ≈0.70m 之後它會**自然變小**
   （手本來就在球附近），不必砍。
2. 砍它＝刪 **27 條測試**，直接違反 §8「測試只增不減（現 750）」，
   而 §9 out-of-scope 沒列、白名單也沒授權。
3. 它是**表現層**，好不好看只有 Sawmah 能裁定（R6 品味判斷）。

階段五要做的是重量 `reach-assist.test.mjs:266-267` 那兩個實測擊球高度
（`2.79`／`3.09` 會隨可及模型漂）＋讓 `REACH.WINDOW_FULL` 跟著 `REACH_RADIUS` 走。
