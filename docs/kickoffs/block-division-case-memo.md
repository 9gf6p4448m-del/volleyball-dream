# 攔網分工案 — 開卷備忘（一頁）

> 2026-07-31 於組合攻擊卷「門 1 真人試玩」回饋中衍生。**非組合攻擊卷的工作量**，另立一卷。
> **排序裁定（Sawmah，2026-07-31）：本卷排在組合攻擊卷之前**——理由見 §三。
> 診斷探針＝`tools/triple-block-probe.mjs`（40 局四臂對照，`src/` 零改動）。

## 一、問題陳述

Sawmah 真人試玩曜石戰回報：**「他們連攔網都會直接三人攔網攔中」**。

實測證實，且比表面嚴重——**三人擠成一堵 1.10m 的牆，在四支隊伍身上一樣成立**：

| 面對 | 曜石(commit) | 曜石強制read | 白浪(非白名單) | 黑松(原生read) |
|---|---|---|---|---|
| 快攻・前排三人 x 全距 p50 | **1.10m** | 1.14m | 1.12m | 1.11m |
| 快攻・三人同時舉手 | **80.2%** | 0.3% | 1.5% | 0.0% |
| 兩翼・三人 x 全距 p50 | **1.10m** | 5.06m | 5.14m | 5.06m |
| 兩翼・牆心離球過網點 p50 | **1.66m** | 0.80m | 0.79m | 0.83m |

**第一列是本案的核心事實**：牆寬與人格無關，四臂完全一樣 ⇒「三人擠中路」不是 commit 造成的，是攔網走位的結構性問題。
**第二列是它為何直到現在才被看見**：只有 commit 隊三人一起離地，read 隊站得一樣擠但根本不跳。

## 二、病灶（全部走真實路徑查證）

1. **共用單一計畫**：`ai.js:203` 的 `aiState.blockPlan` 是**單一欄位**，`ai.js:1220-1221` 只用 `c.team !== team` 判斷歸屬 ⇒ 同隊三名攔網手共用同一份計畫（同一個 `x`、同一個 `enterTick`、同一個 `jumpTick`）。**「不同人攔不同人」在現行資料結構下不可表達。**
2. **牆寬是常數不是湧現**：`ai.js:1668` `xs = front.map((_, i) => anchorX + (i - main) * BLOCK_SHOULDER_M)`，`BLOCK_SHOULDER_M = 0.55`（`ai.js:1639`）⇒ 牆寬恆 1.10m。實測逐值相符（過網 x=0.28 → 在窗 x=[−0.55, 0.00, 0.55]）。
3. **分工約束近乎不存在**：全域只有 `ai.js:1644-1650` 的 `blockFarWing`，條件是 `|anchorX| > 1.8` **且**自己在攻擊點對側 ⇒ **攻擊點在中路時恆為 false，三人必定全部留牆**。`ai.js:1001-1024` 的 `wallBail` 是時間預算不是分工。「每個攻擊手最多幾人攔」「翼攔手責任區」這類規則 `ai.js`／`blockRead.js`／`blockBand.js` **全檔沒有**。
4. **讀期本來是分開的，被計畫蓋掉**：`ai.js:985-992` 讀期走 `nx = anchorX + laneOff`（`laneOff = lane × BLOCK_SPREAD`，`ai.js:65` 為 1.5）＝ ±1.5m 散開；一旦計畫建立就被 `blockWallSlots`（`ai.js:995,997`）覆蓋成 ±0.55m。

## 三、為何排在組合攻擊卷之前

組合攻擊卷的驗收 6.2（交叉／夾塞／他人時間差）與 6.4（假動作騙到 commit）**全部預設攔網手能被個別騙走**。
在「三人共用一份計畫、一起跳同一個點」的結構下，「騙到其中一人」不存在——誘餌只能把整堵牆一起拉走。
⇒ 組合攻擊做完也量不出效果，Δ 會歸因到錯的地方。

**對稱觀察**：攻擊端缺「組合」（每名攻擊手各自抽 route）、防守端缺「分工」（三名攔網手共用一計畫），
是同一個結構層的兩面。兩者都是「把集體拆成個體」的工程。

## 四、止血嘗試——**實測無效，已還原；時序題歸入本案**

commit 的 blind 退路：`ai.js:1250-1256` 讀不到人時把 `x` 寫死 `0`，且 `ai.js:1365` `if (c.blind) return c.x;` **全程不改瞄**
⇒ 曜石打兩翼時整堵牆留在中路（牆心偏離 1.66m ＝兩翼幾乎空門）。

**Sawmah 裁定甲＝解凍改瞄**（2026-07-31）：移除 `ai.js:1365` 的凍結，讓牆在球路明朗後修正瞄準。
**已實作並實測（同探針、同 40 局），結果幾乎無效，Sawmah 裁定還原**：

| 曜石・兩翼 | 解凍前 | 解凍後 |
|---|---|---|
| 牆心離球過網點 p50 | 1.66m | **1.63m** |
| 前排三人 x 全距 p50 | 1.10m | 1.10m（p90 1.17→3.00） |
| 三人同時舉手（畫面口徑） | 60.7% | 54.7% |
| **AI 側三人同時攔** | 3.0% | **1.5%** |

**為什麼無效——這是本案要接手的第五條病灶**：

最後一列說明一切。AI 側只有 1.5%，畫面口徑卻 54.7% ⇒ **球過網時攔網手早就落地了**。
commit 的起跳訊號是助跑下降沿，而 `ai.js:1334-1336` 早已記載：一次兩翼攻擊有好幾個下降沿，
**第一個 p50 = set+35 是中路誘餌拔起**，真正的攻擊手在 set+82。曜石打兩翼的實際流程是——
牆吃了誘餌的下降沿、在 set+35 拔起，球 set+89 才過網，人早落地。

解凍之所以沒用：`blockCommitRead` 只認 `lz ≤ DEPTH_LZ(2.9)` 的候選，兩翼助跑起點 `lz 3.58` 在範圍外
⇒ 那段時間**範圍內唯一看得到的人就是中路誘餌**，解凍讓牆能改瞄，改瞄的結果還是中路。

⇒ **兩翼空門是時序問題，不是瞄準問題。** 它與 §二 的共用單一計畫是同一個地盤
（`blockPlan` 共用同一個 `jumpTick` ⇒ 三人只能一起吃同一個下降沿），故歸入本案。

**還原紀錄**：`git checkout -- src/sim/ai.js`，`src/` 回到 `main@97ef984` 逐值狀態；平衡熔斷未跑（無改動可驗）。
教訓與門 2 的 Q2 A 同型——**裁定指認的那一行不是病灶**（`project_volleyball_dream` memory 已記載此模式重複出現）。

## 五、開卷時要裁的問題

0. **（§四 新增）commit 該吃第幾個下降沿？** 現行吃第一個（p50 set+35＝中路誘餌），真攻擊手在 set+82。
   `ai.js:1339` 明載「該吃第幾個下降沿實質上就是 read／commit 賭局的定義本身（憲法 §零 領域），
   不由實作端自行決定」，且實測試過「下降沿要認人」會退步（read 面對快攻 100% 不起跳）。
   ⇒ 這題必須連同 per-blocker 拆分一起想：三人共用一個 `jumpTick` 時，「一人吃誘餌、兩人等真攻擊手」
   在結構上無法表達。
1. **計畫要不要拆成 per-blocker？**（`aiState.blockPlan` 單一欄位 → 每名攔網手一份）這是本案最大的工程量，也是「個別騙得到」的唯一前提。若不拆，§三 的依賴就解不開。
2. **分工規則長什麼樣？**——「單一攻擊點最多 2 人上牆」／「翼攔手責任區」／「第三人回落補吊球」擇一或組合？幅度多少？
3. **牆寬 `BLOCK_SHOULDER_M=0.55` 該不該動？** 它現在是三人牆的唯一決定因素；分工落地後它的角色會變。
4. **上位問題：這是否為「防守端個體化」系列的第一案？** 若接發／防守站位也共用類似的集體結構，應一併規劃而非單點補丁。
