## 零、這一卷為什麼是地基

W1 加了四件「讓對方判斷錯誤」的武器——**跳舉、交叉、commit 人格、假扣真傳**——
但對手**沒有會判斷錯誤的機制**。三個地方 sim 給了球員超人能力：

| # | 現況 | 讓什麼變成裝飾 |
|---|---|---|
| 十-1 | 觸球判定水平 **1.3m**、垂直可到站立摸高 | 手臂長度、走位品質（反正搆得到） |
| 十-2 | 攔網手**零反應延遲**（接球手有、攔網手沒有） | read／commit 的賭局 |
| 十-3 | 攔網結算**只認一個人** | 雙人／三人牆、三線分工、close 時間預算 |

**四件武器全部卡在這裡。§十 不只是「讓 sim 誠實」，它是「讓欺敵有意義」的地基。**

## 一、待拍板題

### Q1｜觸球判定的目標值該是多少？（十-1）
現況水平 1.3m。真實排球的手臂可及是多少？**水平與垂直要分開定**——
W1 量到落差的**大頭是垂直不是水平**（見工程事實 §2）。

需要拍板的：
- 各動作（接球／舉球／扣球／攔網／魚躍）的**目標可及範圍**
- 是否該**依球員屬性變化**（身高、臂展）——現在 `REACH_RADIUS` 是全隊共用的常數，
  而 `standingReach` 是 `身高 × 1.31`。判定半徑要不要也吃身高？
  （**這會直接影響「真實身高系統」的體感**——`design-brief.md:9` 的核心賣點）

### Q2｜攔網手的反應時間該是多少？（十-2）
接球手現有 `reactionTicks = max(6, 24 − reaction×0.16)` ＝ **0.10–0.40 秒**。
攔網手目前是 **0**。

需要拍板的：
- 攔網手的反應延遲該用同一條公式，還是另一條？
- **關鍵**：延遲要從**什麼事件**起算？（二傳觸球？攻擊手起跳？球離手？）
  ——這決定了 commit 賭注的形狀。commit 是「不等那個事件就先動」，
  所以起算點就是賭注的內容
- 真實排球中 read 攔網手**追不到快攻**是常態嗎？還是只是「比較吃虧」？

### Q3｜牆的模型長什麼樣？（十-3）
憲法已寫死「**必須是覆蓋一個橫向帶，人數與間距決定帶寬**，不得只是人數×機率加成」。
但帶寬怎麼算是設計題：

- **帶寬公式**：一個人多寬？兩人並肩多寬？中間有縫隙嗎？
- **擦手（one-touch）**：現在是攔死判定之後的第二段（`BLOCK_GRAZE_CHANCE 0.22`）。
  改成帶模型後，擦手該是「打在帶的邊緣」嗎？
- **縫隙**：真實排球打「手縫」是重要戰術。要不要做？做了的話，
  它會變成攻擊手的另一個目標（現在 `attackZones` 只有直線／斜線／短球）
- **高度**：現在 `blockReach = standingReach + 起跳 × 0.85`，球高過手就攔不到。
  帶模型要不要也吃高度（＝一個矩形而非線段）？

### Q4｜rally 長度的目標是多少？
判定變嚴 ⇒ 更多球接不到 ⇒ rally 變短。憲法協議第 4 條已寫「**rally 變短不預設是壞事**」，
但「多短才好玩」是純品味題，**只能由 Sawmah 定**。

需要一個可驗收的目標（例如「平均來回次數」或「每分平均時長」），
否則分段收斂沒有停止條件。

### Q5｜難度重算後，錨點是什麼？
本卷必然重算難度曲線。W1 結束時：**決賽帶 21%／奪冠 4%**（4.7 基線是 31%／9%）。

需要拍板的：
- 重算後要回到 4.7 基線，還是接受新的錨點？
- **注意**：W1 的位移主因是 D2 的池降級（工單指定機制，不是 bug），
  而且**場均殺球反而上升**（3.42→3.45）＝不是玩家變弱，是攻防都變複雜

### Q6｜三件事的實作順序
憲法協議第 6 條寫「**一起校準，不得逐件收斂**」（逐件調會各自過頭）。
但**實作**可以有順序。建議討論：先做哪一件、什麼時候開始合併校準。

| `BLOCK_LATE_MUL` / `BLOCK_EARLY_MUL` | 0.6 / 0.55 | 太晚／太早的折扣 |

### C. 攔網結算只認一人（`src/sim/game.js:882-893, 920`）
```js
for (const p of ...) { ... if (!best || dx < best.dx || ...) best = { p, actor, dx }; }
if (!best) return false;
const chance = (0.12 + best.p.attributes.block * 0.004) * timingMul * scoutBlockMul(...);
```
迴圈掃過所有合格攔網手，**只留 dx 最小的一個**，用**他一人**的 `block` 屬性擲骰
⇒ **雙人／三人攔網的成功率與單人完全相同**。

## 四、Claude.ai 五條質疑的實測裁決（2026-07-29 回填）

> Claude.ai 讀完本簡報後提出五條「前提可能不成立」。實測結果：**四條成立、一條推翻**。
> **其中第 1 條改變了 Q1 的答案形狀**，本節的結論優先於前文。

### ① 「扣球的落差是表現層欠債，不是判定太寬」— **成立，前文有誤**

實測（5 seeds，逐次觸球取該球員的真實 `standingReach`／`spikeReach`）：

| 觸球 | 球高 p50 | 該員**站立**摸高 | 該員**起跳**摸高 | 球高 − 站立摸高 |
|---|---|---|---|---|
| 接球 | 1.65 m | 2.46 m | 3.15 m | −0.81 m |
| **舉球** | **2.82 m** | **2.40 m** | 3.09 m | **＋0.43 m** |
| **扣球** | **3.07 m** | 2.46 m | **3.15 m** | ＋0.61 m |

- **舉球＝sim 太寬**：二傳**不跳**（`overhead` 序列 `jump: 0`），卻在自己指尖上方 **43cm** 觸球。
  成因＝`touchCeiling` 的 `standingReach + 0.35`（`src/sim/ai.js:1083`）——**站著搆過指尖 35cm**
- **扣球＝sim 垂直沒有太寬**：球高 3.07m **在該員起跳摸高 3.15m 之內**，物理一致
- **前文「球在手上方 0.69–0.73m」的算法有誤**：那是拿**世界座標的球高**減**身體本地座標的手高**。
  `reachAssist.js` 的 `handPos()` 回傳的 `up` 由 `SPINE_Y + 肩 + 上臂 + 前臂` 疊出，
  **不含跳躍位移**，而 `spike` 序列自帶 `jump: 0.55`。實際扣球落差 ≈ 3.07 −(2.4+0.55) ＝ **0.12m**

> **⇒ Q1 不是「一律縮」：舉球收 sim、扣球補動畫，兩件不同的活。**
> 舉球另有動畫欠債（手只到 2.0m，低於該員自己的站立摸高 2.40m），兩者疊加才是 0.79m 的視覺落差。

### ② 「一傳品質恆 perfect 是獨立 bug，十-1 收緊後會自己長出分佈」— **推翻**

`passTier` 確實是**導出值**不是獨立骰（`passTierOf(team, landing)` 吃預測落地點離二傳位置的距離，
而落點散佈吃 `receiveQualityMul(dist, REACH_RADIUS, player)`）。**但幅度遠遠不夠**：

```
passTierOf 實際吃到的距離（n=124，10 seeds）
  p50=0.23  p75=0.35  p90=0.44  p99=0.51  max=0.53      ← 門檻是 1.2
  若散佈 ×1.1 ／×1.22 ／×1.5 ／×2.0 → 掉出 perfect 的比例皆為 0.0%
```

到位程度在 `TUNING` 裡是**刻意的次要修正**（`RECV_POS_MIN 0.9` → 勉強 ×1.1，僅 ±10%，
註解明寫「不主導」），主軸是接球技術。**真正的成因是門檻（1.2m）相對實際散佈（max 0.53m）
太寬鬆**——要動的是散佈量／門檻／「壓力下瞄不準」，**是獨立槓桿**。
**⇒ H 維持獨立題，不因十-1 而自動解決。**

### ③ 「`BLOCK_REACH_X 1.1` 是半徑」— **成立，且比預期嚴重**

`src/sim/game.js:899`：`const dx = Math.abs(actor.x - b.x); if (dx > TUNING.BLOCK_REACH_X) continue;`
⇒ **半徑，單人涵蓋全寬 2.2m**。真實排球單人雙臂展開約 1.0m、雙人牆 1.5–1.8m
⇒ **現在單人就比真實雙人牆還寬**。**Q3 的起點數字差約一倍。**

### ④ 「玩家與 AI 的攔網反應約束不可比」— **成立**

`game.js:427`：`actor.blockUntil = state.tick + TUNING.BLOCK_WINDOW`，
**從 block intent 抵達那一刻起算**（玩家＝按鈕、AI＝決策）。
**補充**：玩家的「延遲」是他自己的反應，而 `blockTimingMul`（甜蜜區 4–26 tick）
已在懲罰太早太晚 ⇒ **Q2 真正要定的是「AI 的延遲該不該比人類慢」**，而非「要不要有延遲」。

### ⑤ 「觸球判定用球心、不吃球半徑」— **成立，且有不一致**

`game.js:454-455`：`dist = hypot(ball.x−actor.x, ball.z−actor.z)`，純球心對球心，**不吃 `BALL.RADIUS`**。
**但攔網高度判定有吃**（`b.y > blockReach(p, ...) + BALL.RADIUS`）
⇒ **同一套判定裡兩種標準**，本卷應一併統一。
