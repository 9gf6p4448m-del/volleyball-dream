### ★ 一顆前車之雷（08-24 事故的直接教訓）★

配色要從資料層流到 `matchView`，**接線大概率經過 `main.js` 附近的組裝層——
node 測試對它零覆蓋**（生涯選單 ReferenceError 活了 10 天就是這樣來的）。
⇒ 本卷驗收**必含瀏覽器層驗證**（實開一場比賽看到對手穿隊色），不得只憑 node 綠。

## 三、題目（一輪整批，各附建議答案）

**題 1 我方球衣要不要也換？**
- A案：我方恆定現行藍，只有對手逐隊換色（可讀性零風險，改動面最小）
- B案：我方也有隊色——高中先取校名＋校色、大學穿選校色（沉浸感最高，但要先解決「我方隊名不存在」，且敵我判讀改依賴 UI 語意色通道）
- C案：階段一走 A，「大學選了哪所就穿那所球衣」列階段二待辦（排序不縮減，比照大學卷慣例）
- ➡️ 建議 **C**：先兌現使用者原話的痛點（對手千人一面），選校穿校色是好故事但牽動我方身分設計，等大學卷試玩過再議。

**題 2 撞色怎麼治理（對手隊色撞我方藍、或撞 UI 青）？**
- ➡️ 建議：**設計時保證＋測試守門，零 runtime 機制**——16 隊色票設計時就與我方藍／UI 青拉開距離，並寫 pairwise 色距斷言（門檻實作前量定）永久守住；不做「客場副色」「自動挑對比色」這類 runtime 系統（Simplicity First）。

**題 3 十六隊的色票誰定、怎麼定？**
- ➡️ 建議：我出**整套提案表**（每隊：主色／短褲／滾邊／自由人色＋一句理由，錨定隊名意象與球風，天鷹沿用既有 `#7db2ff`），配預覽治具截圖給使用者**看圖裁定**——色彩是品味題（03 R6），不擅自定案。

**題 4 本卷範圍要不要含 UI 點綴？**
- ➡️ 建議最小集：①球衣 ②宿敵橫幅改吃資料色（機件已在，一行接線）③其餘（對陣畫面隊色徽章、賽程表色塊、觀眾席應援色）列待辦。**記分板／氣勢計／頭上標籤的敵我語意色一律不動**——那是玩家練了十幾卷的操作語言。

**題 5 自由人異色（FIVB 對比色）怎麼配？**
- ➡️ 建議：**每隊手設進色票表**，設計時保證與該隊主色對比，寫進同一條色距斷言；不做自動衍生演算法。

**題 6 預覽治具要不要做？**
- ➡️ 建議：**做**，比照 `?devseed` 慣例加 `?devkit` 預覽舞台（複用 `recruitPortrait`／立牌機件，一頁看全部隊伍球衣＋自由人）——它同時是題 3 的裁定工具與驗收 K2 的量測工具。

## 四、範圍草案（依題 1 答案微調；以下按 C 案寫）

依相依序：
1. **資料層加 `kit` 欄位**（`opponents.js` 7 隊、`universities.js` 9 校）＋
   單一取用入口 `kitFor(def)`（缺欄位回落現行紅色預設——未來新增隊不炸）。
2. **`createGeoCharacter` 增 kit 參數**（預設回退現行 `TEAM_KIT[teamId]`，4 個呼叫端零強迫遷移）。
3. **接線**：`matchOpponentDef` → 比賽組裝層 → `matchView`，對手側改穿隊色（★經過 main.js，見二之雷★）。
4. **宿敵橫幅**改吃 `kit` 資料色，移除 `main.js:202` 寫死值。
5. **`?devkit` 預覽治具**。
6. **色票提案表**（我產）→ 使用者裁定 → 定案寫入資料層。
