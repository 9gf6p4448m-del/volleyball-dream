## 〇、動手前必讀的三件事

### 1. 真交叉在現行幾何下**可符號證明恆假**

驗收 6.2 第一條「主攻者路徑確實穿過配合者起跳點後方」——

## 二、組合結構

**放哪**：`aiState.attackCombo`，與 `attackerId`／`approach` **同壽命同重算範式**
（一傳完成算一次；`ai.js:245`（非 rally）與 `ai.js:407`（來球）兩處清空）。

```js
// null ＝ 本波沒有組合 ＝ 現行單人行為（退路分支）
{
  type: 'cross' | 'tandem' | 'delay',
  mainId,        // ＝ attackerId（冗餘，讓消費端不必跨欄位對照）
  partnerId,     // 配合者
  tempoGap,      // 裁定 D 丙＝本段留白
  mainKind, partnerKind,   // 幾何自證欄位，探針與測試直接讀
}
```

**為什麼不塞進 `approach.routes`**：routes 是 per-pid 平表，組合是 pid 對之間的關係。
塞進去會讓每筆帶著對方的資訊，打破 `myRoute.js` 的「不外洩未來值」約束。

**為什麼不改 `attackKind` 的值域**：它進了 Q4 記帳與跨賽季存檔，改值域要處理存檔遷移
（上位裁定書 §三.4 特地提早改名就是為了同一個理由）。

## 三、排程順序（裁定 A 乙的形狀）

```
attackPointsOf                        // 池不變
  → applyRouteKinds(points)           // 現行單人抽籤，不動（left_inside 保留）
  → pickAttackPoint(…)                // 【不動】trust 照現行抽出主攻者
  → planCombination(points, mainId)    // 【新】由主攻者的 kind 決定能不能組合、配誰
  → applyComboRoutes(points, combo)   // 【新】把 combo 的 kind 寫回池（只動涉及的兩人）
  → approachRoutesFor(points, {combo})// tempo 優先吃 combo，其餘維持現行 hash
```

⚠ `pickAttackPoint` 一格未動＝trust 分佈逐值不變，這是裁定 A 乙的驗收條件本身。

## 四、三型的可機械判定條件

全部只吃 `approach.routes` 與實跑座標，不吃未來值。

### 交叉 `cross`
1. `partner.kind === 'quick'`
2. **穿越**：主攻者助跑線段 `start → takeoff` 的 lx 區間包含 `partner.takeoff.lx`（＝0）
3. **後方**：線段在 lx＝0 處的 lz > `partner.takeoff.lz`（＝1.68）
4. **前後腳**：兩人**物理起跳 tick** 差 ≥ 門檻（門檻先量再定）
5. **搆不到**：主攻擊球點離快攻點 > `TUNING.BLOCK_REACH_X`

幾何試算（未實跑）：起點 (−4.1, 3.6) → 起跳 (+0.9, 1.98) 的線段在 lx=0 處 lz ≈ **2.27 > 1.68**，餘裕 0.6m。

### 夾塞 `tandem`
1. **同線**：`|Δlx| ≤ TANDEM_LANE_M`（建議 0.6m）
2. **前後疊**：`Δlz ≥ TANDEM_DEPTH_M`，**硬下界 > `SEP_RADIUS = 0.55`**
   （否則同隊避讓會把兩人推開、幾何自我瓦解＝恆真但無意義）
3. **節奏錯開**：物理起跳 tick 差 ≥ 門檻
4. **不得同時滿足交叉條件 2**（兩型互斥，避免雙重計數）

### 他人時間差 `delay`
1. partner 物理起跳 < main 物理起跳
2. partner 落地 tick（物理起跳 + `AIR_TICKS` 24）落在 main 擊球 tick 的 ±`DELAY_WINDOW` 內
3. **需有探針計數**（驗收 6.2 明文）

⚠ 現值試算：一速誘餌落地 39 vs 二速主攻擊球 ≈ 55 ⇒ **差 16 tick**。
窗取 ±8 恆假、取 ±20 幾乎恆真。**不得憑試算寫死門檻，先量實際分佈。**

## 六、必須知道的相容性風險

| 項目 | 風險 |
|---|---|
| **誘餌湧現式** | 結構上不需要旗標（池內每個 point 都拿到完整 route）。但 `attackCombo.partnerId` 語意上非常接近誘餌旗標 ⇒ **加靜態掃描**：sim 走位分支（`ai.js:1100-1133`）不得出現 `attackCombo`／`partnerId` 字樣（比照 `block-persona.test.mjs` 的 B1-SCAN 範式） |
| **`blockWallSlots` 壓平效應** | `ai.js:1780-1834` 三人佈局全由**一個** `anchorX` 導出、肩距 0.55。即使兩名攔網手 `c.x` 分歧，佈局會把他們重排成連續的牆 ⇒ **驗收 6.2 不應以「牆散開」為指標**，應以 `jumpTick` 分歧與實際攔網結果為指標 |
| **`DEPTH_LZ = 2.9`** | commit 只看得見 lz ≤ 2.9 的候選。新線起點 lz > 2.9 就隱形 ⇒ 「他人時間差」要騙 commit，誘餌**必須先進入可見帶再消失**（下降沿的成立前提） |
| **Q4 記帳靜默丟棄** | `game.js:659` 的 `!== undefined` 守衛在新 kind 未加鍵時**不報錯、直接不記**。新增 kind 必須同步改 `game.js:365-367` **與** `careerState.js` 的跨場累積 |
| **VCR v2** | `tests/rally-tape-approach.test.mjs` 逐值比對 `aiState.approach`。AI 產出的 combo＝重算即可；玩家指定的必須進 `rallyTape.js` 的 `PLAYER_AI_FIELDS` |
| **`AIR_TICKS = 24`** | 同時是踏線違例回溯窗（`approach.js:228`）——組合的時序設計**不得動這個常數** |
| **驗收 6.1 需重跑** | 組合會改變二速的出現分佈 ⇒ 罰站率／attack-flow 全表／三檔飛行時間／`TAKEOFF_*` 未動 四條都要重驗 |
